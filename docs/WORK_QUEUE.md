# Work queue

Generated by `scripts/work_queue.py`; do not edit by hand (defer tools in `docs/WORK_QUEUE_DEFERRED.txt`). Order: inventory priority (P0 first), then toolbox (most-used first), then tools whose output ArcGIS lets us reproduce exactly, then easier ones. Tools that need a server or enterprise database, and tools that only manage map layers, come after all others.

## How agents use this queue

1. **Finish or wrap up the current tool first.** If the work in progress is polish on a tool that
   already landed (byte-level differences, rare parameter combinations), commit what is validated,
   record the rest in `docs/KNOWN_GAPS.md`, and move on.
2. **Then take the first open item in "App priorities"** (basic app functionality, from
   `docs/APP_PRIORITIES.md`; tick it there when it lands). Only when none is open, take the first
   tool in "Up next" that is not deferred. Skip only for a concrete reason.
3. **One tool = one landing.** Implement the default and commonly used parameters, add ArcGIS
   reference cases, pass `scripts/check`, then commit and push. Never push with `--no-verify`: the
   pre-push hook checks the commit itself, and uncommitted edits can make a working-tree check pass
   while CI fails. Options not covered go to the roadmap and known gaps, not to the next action.
4. **Time box: about two coordinator turns per tool.** If a tool is not converging (untestable,
   random output, needs a licence/ArcSDE/enterprise geodatabase, or a format we cannot write yet),
   add a line to `docs/WORK_QUEUE_DEFERRED.txt` with the reason and take the next one.
5. After each landing run `python3 scripts/work_queue.py` (the post-commit hook also does) and make
   the handoff's next action "next queue item: <tool>".
6. A user request always comes first. Polish of landed tools happens only when asked.
